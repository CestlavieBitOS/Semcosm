# SOSP：结构化对象规格说明范式

> **Structured Object Specification Paradigm**
>
> **文档状态**：正式版v1  
> **文档形式**：正式 Markdown 文稿  
> **适用对象**：以 C 或类 C 语言为主要实现载体、需要长期维护数据对象定义与说明文档的一类工程体系

---

## 摘要

SOSP（Structured Object Specification Paradigm，结构化对象规格说明范式）旨在建立一套**无歧义、可维护、可自动检查、可生成正式文档**的数据对象说明体系。它关注的不仅是“对象有哪些字段”，更关注“对象表示什么、由谁拥有、在何处定义、哪些状态合法、是否参与 ABI / IPC / 持久化，以及文档如何与代码层级、代码类型和自动化治理保持一致”。

本文档给出 SOSP 的核心原则、对象描述模型、模块文档组织方式、项目级目录结构，以及自动化落地建议。整体目标是在工程实践中形成一套可持续演化的对象文档治理方法，使对象说明既能服务开发协作，也能支撑评审、归档、交付和自动检查。

---

## 1. 背景与目标

在中大型工程中，数据对象往往同时出现在代码、接口说明、设计文档、协议说明、持久化格式说明等多个位置。一旦缺少统一的对象规格体系，常见问题会迅速出现：同一对象在多个文件中被重复定义、字段名与代码命名漂移、结构与语义混写导致误读、模块边界逐渐模糊、公共层被过度膨胀、文档目录与代码目录失去对应关系，最终使文档难以维护，也难以纳入自动化检查。

SOSP 的目标，是为这类问题提供一套统一的方法论与规范框架。该框架应满足以下要求：

- 明确对象的**定义**与**语义**，避免“结构相似即语义相同”的误判。
- 明确对象的**拥有者**、**可见性**、**归属文件**与**跨模块关系**。
- 明确对象的**合法状态**、**生命周期**、**布局约束**与**编码规则**。
- 明确文档如何与代码目录、代码头文件、实现文件及自动化检查保持一致。
- 支持通过结构化数据生成 Markdown、Typst 乃至 PDF 等不同形态的输出。

因此，SOSP 既是一套文档组织规范，也是一套面向工程治理的对象规格描述范式。

---

## 2. 适用范围

SOSP 适用于以下场景：

1. 代码中存在大量 `struct`、`enum`、`union`、别名、句柄等数据对象，需要形成统一说明体系。
2. 对象需要跨模块引用，但又必须保持边界清晰、拥有者明确。
3. 某些对象涉及 ABI、IPC、序列化、落盘、协议传输等，对布局和编码有显式约束。
4. 团队希望将对象文档纳入仓库治理、代码评审与 CI 检查。
5. 团队既需要日常可维护的 Markdown 文档，也需要可正式交付的排版输出。

对于规模较小、对象数量有限、模块边界单纯的项目，SOSP 可按轻量模式使用；对于大型系统，则可以完整采用其结构化真源、生成器和校验链路。

---

## 3. 规范性表述

本文档采用以下规范性用语：

- **必须**：表示不可省略的硬性要求。
- **应**：表示强烈建议遵循的要求；如有例外，应有明确理由。
- **可**：表示允许的可选做法。

为避免术语歧义，本文还采用以下约定：

- **对象**：指被文档说明的类型实体，例如结构体、枚举、联合、别名、句柄等。
- **归属文件**：指某一对象的唯一规范定义所在的文档文件。
- **拥有者（owner）**：指在工程边界上对该对象负责的模块或路径。
- **可见性（visibility）**：指对象对模块外是否可见，通常区分为 `public` 与 `internal`。
- **源事实层**：指保存对象结构化定义的真源层。
- **渲染层**：指由真源生成的可读文档层，如 Markdown、Typst 或 PDF。

---

## 4. 六项总原则

### 4.1 一个对象只能有一个归属文件

一个对象**必须**只有一个归属文件。谁拥有它，谁定义它；其他位置只能引用，不能复制粘贴并重新定义。

这是避免文档漂移和边界混乱的基础。如果同一对象在多个模块文档中以“局部复制”的方式出现，随着代码演化，这些副本必然发生细微差异，进而导致读者难以判断哪个定义才是当前有效定义。SOSP 因此要求对象定义唯一，引用显式，来源可追踪。

### 4.2 文档应尽量直接映射到 C

文档中的类型名、字段名、位宽、单位和命名形式，**应**尽量与 C 代码保持一一对应。例如，若代码使用 `int64_t`，文档就不应写作 `int64`；若字段名在代码中为 `timeout_ms`，文档中也不应改写成 `timeout` 或 `timeoutMillis`。

这种映射并非纯粹追求形式一致，而是为了降低长期维护中的漂移风险。短期看似无害的小差异，在版本演进、多人协作、自动化生成与静态检查过程中，都会不断放大。

### 4.3 对象定义与对象语义必须分离

对象说明中，**定义**与**语义**必须分离。`repr` 负责说明“对象长什么样”，`semantics` 负责说明“对象表示什么”。

这条原则尤其适用于时间值、索引、句柄、状态对象、标识符对象等。许多对象在字段层面上可能完全相同，但其实际含义、使用方式、零值含义和合法状态却完全不同。若将结构和语义混写，读者极易在相似形式之间误判语义。

### 4.4 不把共享当作默认

对象默认应属于某个具体模块。只有当某对象被多个模块复用，且其语义本身独立于单一模块时，才应提升到 `common` 层。

公共层不是“暂时想不清楚放哪里”的缓冲区。把共享当作默认，会导致 `common` 逐步膨胀，模块边界变得松散，最终使对象治理退化为“到处都能用、谁也不负责”。因此，SOSP 要求默认私有、按需提升，而非默认共享。

### 4.5 同类对象顺序固定

所有模块文件**应**按固定章节顺序组织；对象在模块文件内部也**应**按统一类别顺序排布。理想状态下，这种顺序不依赖人工自觉，而由生成器强制输出。

固定顺序的意义不只是“排版好看”，更在于稳定阅读路径、减少 diff 噪声、让检查规则可自动化，并使不同模块文档呈现出一致的认知结构。

### 4.6 文档层级反映代码层级

文档目录**应**尽量镜像代码目录，尤其要与 `include/` 和 `src/` 的模块层次保持可推导关系。这样维护成本最低，也最容易落地自动检查。

当文档层级与代码层级脱节时，评审者难以知道一份文档对应哪个头文件，开发者难以判断一个对象是否属于公共接口，自动化工具也无法稳健地检查目录映射、文件边界与可见性一致性。

---

## 5. 总体架构：两层分离

SOSP 的总体结论是：对象文档体系应坚持**源事实层**与**渲染层**分离。

### 5.1 源事实层

源事实层使用结构化模型保存对象定义，可采用 `CUE`、`YAML`、`JSON` 等形式。该层是对象规格的真源，应至少承载以下信息：

- `name`
- `c_type`
- `owner`
- `visibility`
- `repr`
- `semantics`
- `invariants`
- `relations`
- `doc_path`
- `code_path`

必要时，还可扩展 `field_notes`、`lifetime`、`layout`、`encoding`、`versioning`、`stability` 等字段。

### 5.2 渲染层

渲染层负责将真源转化为可读文档，包括 Markdown、Typst 以及最终 PDF。Markdown 和 Typst 都不应被视为唯一真源，而应作为结构化数据的生成结果。

只有将规则治理建立在更底层的结构化数据上，才能真正检查以下约束：

- 对象唯一归属
- 定义与语义分离
- 公共层与模块层边界
- 对象及章节顺序
- 文档目录与代码目录映射
- 生成结果是否为最新版本

### 5.3 分层原则的价值

这种分层使工程拥有两个互不冲突的目标：一方面，开发者可以继续使用 Markdown 进行日常阅读、协作和评审；另一方面，工程治理又不必依赖人工维护文本一致性，而可以通过结构化真源、schema、lint 和 CI 形成稳定的自动化链路。

## 6. 单个对象的标准规格

### 6.1 基本要求

每个对象都应拥有完整且可检查的规格条目。一个合格的对象条目，不应只包含字段结构，还应明确其语义、合法状态、字段说明、生命周期和与其他对象的关系。

推荐的对象规格字段如下：

- `name`：对象名。
- `c_type`：代码中的真实 C 类型名。
- `kind`：对象类别，通常为 `struct`、`enum`、`union`、`alias`、`handle` 之一。
- `owner`：对象拥有者。
- `visibility`：对象可见性，通常为 `public` 或 `internal`。
- `repr`：对象的结构表示。
- `semantics`：对象所表示的实际含义。
- `invariants`：对象合法状态约束。
- `field_notes`：字段补充说明。
- `lifetime`：资源所有权、拷贝规则与生命周期约束。
- `layout`：内存布局稳定性相关要求。
- `encoding`：序列化或传输编码要求。
- `relations`：与其他对象的依赖、包含或引用关系。

### 6.2 推荐模板

```yaml
# Object_Name

c_type: object_name
kind: struct | enum | union | alias | handle
owner: module/path
visibility: public | internal

repr:
  struct {
      field_a: int32_t;
      field_b: uint16_t;
  }

semantics:
  - 它表示什么
  - 它不表示什么
  - 它的零值 / 缺省值是什么意思

invariants:
  - 合法状态约束 1
  - 合法状态约束 2

field_notes:
  - field_a: 单位是 ms
  - field_b: 只有当 xxx 时有效

lifetime:
  - value object | borrowed | owning
  - 是否允许浅拷贝

layout:
  - 是否要求稳定内存布局
  - 是否允许 padding
  - 是否参与 ABI / IPC / 持久化

encoding:
  - 小端 / 大端
  - 对齐要求
  - 版本字段规则

relations:
  - depends on: Foo_Id, Time_Spec
```

### 6.3 结构与语义的边界

`repr` 用于陈述对象在代码层面的形态，例如字段、位宽、类型名和组合关系；`semantics` 用于陈述对象在业务和系统层面的含义，例如对象代表哪个时间语义、哪个状态域、哪个资源的句柄，以及零值、空值、默认值分别意味着什么。

一个成熟的对象规格必须允许读者分别回答两个问题：

1. 这个对象在代码里是什么形状？
2. 这个对象在系统里意味着什么？

若这两个问题无法被清晰区分，说明对象文档尚不合格。

### 6.4 不可省略的补充信息

对于以下类型的对象，应增加更严格的说明：

- **带单位的数值字段**：必须写清单位，例如 `ms`、`byte`、`ns`、`tick`。
- **成对或耦合字段**：必须说明耦合关系，例如 `ptr + len`、`buf + size + capacity`、`base + count`。
- **带资源所有权的对象**：必须说明其为 `borrowed` 还是 `owning`，是否允许浅拷贝，是否必须显式 clone。
- **参与序列化或传输的对象**：必须说明布局、字节序、对齐、padding、版本字段和保留字段约束。

## 7. 对象之间的引用规则

为保证对象边界稳定，文件之间的引用规则应提升为硬性约束。

### 7.1 只引用，不复制

若某模块使用外部对象，应写显式依赖，而不是在本模块文档中再抄写一遍定义。例如：

```yaml
relations:
  - depends on: common/time :: Time_Spec
```

而不是在 `scheduler` 模块文件中重新定义 `Time_Spec`。

### 7.2 每个对象都必须声明 owner

每个对象都必须写明 `owner`。即使当前边界看似明显，也不应依赖读者推断。显式声明拥有者，有助于后续迁移、拆分或提升到 `common` 时保持边界清晰。

### 7.3 跨模块依赖应尽量通过 common

模块 A 不应直接依赖模块 B 的私有对象。若某对象确实需要被多个模块共享，且其语义独立，应将其抽取为公共对象并迁移到 `common` 层；若不满足这一条件，则应保持拥有者唯一，不应形成隐式跨模块私有耦合。

### 7.4 visibility 必须显式写出

对象是 `public` 还是 `internal`，必须显式写出，不能靠目录位置、文件名或上下文让人猜测。可见性一旦隐含，文档与代码很容易在接口边界上产生不一致。

## 8. 模块级文档组织

### 8.1 默认规则：一个模块一份主类型文件

默认情况下，一个模块对应一份主类型文档。该文档应按固定章节组织，推荐结构如下：

```md
# scheduler.types
## 1. Scope
## 2. Imports
## 3. Naming Rules
## 4. Public Objects
## 5. Internal Objects
## 6. Object Relations
## 7. Notes
```

### 8.2 各章节职责

- `Scope`：说明本文件覆盖的对象范围和模块边界。
- `Imports`：列出本模块依赖的外部对象，但不重复定义。
- `Naming Rules`：说明本模块适用的命名约束。
- `Public Objects`：列出模块对外可见的对象。
- `Internal Objects`：列出模块内部对象。
- `Object Relations`：说明对象之间的包含、依赖、引用或转换关系。
- `Notes`：记录特殊约束、迁移说明、兼容性说明和版本备注。

### 8.3 模块文件内部的对象顺序

模块文件内部的对象应按依赖从浅到深排列，推荐顺序如下：

1. 基础别名
2. 枚举 / 位标志
3. 小型值对象
4. 核心结构体
5. 内部辅助结构

这种顺序使读者先看到叶子类型，再看到依赖它们的大对象，从而形成稳定、可复用的阅读路径。

### 8.4 何时拆分模块文件

默认是一模块一份主文件，但不意味着所有对象都应无限堆叠在同一文档中。拆分应依据**语义边界**，而不是依据页数、行数或排版习惯。

#### 8.4.1 保持不拆的情形

以下情况下，通常可保持单文件：

- 模块对象数量较少；
- `public` 与 `internal` 对象规模都不大；
- 不涉及 `wire`、协议、持久化或 IPC 对象。

#### 8.4.2 应拆分的情形

当出现以下情况时，应考虑拆分：

**（1）公有对象与内部对象差异很大**

可拆为：

- `scheduler.types.md`
- `scheduler.internal.types.md`

**（2）存在协议、存储、IPC 或落盘格式**

应另拆出专门文件，例如：

- `scheduler.wire.types.md`

内存对象关注语义、所有权和生命周期；线上或落盘对象关注布局、字节序和兼容性。这两类说明不应长期混写。

**（3）模块规模很大且代码本身已存在稳定子域**

可按子域拆分，例如：

- `net.packet.types.md`
- `net.session.types.md`
- `net.route.types.md`

但前提是这些子域在代码层面本来就存在，而不是为了文档美观而强行切分。

## 9. 项目级文档目录组织

### 9.1 三层目录结构

整个项目的对象文档，推荐按三层组织。

#### 第一层：项目级规范

```text
docs/data-model/
    00-conventions.md
```

该层只写规则，不写业务对象。其内容包括：

- 命名约定
- 块顺序
- `public` / `internal` 判定规则
- `invariant` 书写方式
- 何时进入 `common`
- 何时拆 `wire` 文件

#### 第二层：公共对象

```text
docs/data-model/common/
    scalar.types.md
    time.types.md
    result.types.md
    id.types.md
```

该层只放真正跨模块共享、且语义独立的对象。

#### 第三层：模块对象

```text
docs/data-model/modules/
    scheduler/
        scheduler.types.md
        scheduler.internal.types.md
    net/
        net.types.md
        net.wire.types.md
    storage/
        storage.types.md
```

### 9.2 文档目录与代码目录镜像

SOSP 强调文档目录应尽量镜像代码目录。例如：

代码目录：

```text
include/project/common/time_types.h
include/project/scheduler/scheduler_types.h
src/scheduler/scheduler_types_internal.h
src/net/net_wire.h
```

对应文档目录：

```text
docs/data-model/common/time.types.md
docs/data-model/modules/scheduler/scheduler.types.md
docs/data-model/modules/scheduler/scheduler.internal.types.md
docs/data-model/modules/net/net.wire.types.md
```

这种映射关系能够直接支撑以下判断：

- 哪份文档对应哪个头文件；
- 哪些对象属于公共接口；
- 哪些对象仅在 `src/` 内部使用；
- 哪些对象涉及 `wire` 或持久化表示；
- 文档路径与代码路径是否仍然一致。

## 10. 自动化方案与 CI 治理

### 10.1 真源不应是 Markdown 或 Typst

Markdown 与 Typst 都不应承担“唯一真源”的职责。真正可校验、可治理、可生成的源头，应是结构化对象模型。Markdown 与 Typst 是其渲染结果，而不是治理入口。

### 10.2 推荐自动化链路

推荐的工程链路如下：

```text
结构化源（CUE / YAML / JSON）
        ↓
schema 校验
        ↓
项目规则 lint
        ↓
生成 Markdown / Typst
        ↓
CI 检查生成结果是否最新
```

### 10.3 适合自动检查的规则

以下规则非常适合自动化落地：

- **唯一归属**：全仓检查 `object_name` / `c_type` 唯一。
- **定义与语义分离**：schema 强制对象必须包含 `repr`、`semantics`、`invariants`。
- **默认模块私有**：lint 检查 `owner`、`visibility` 与 `common` 的使用是否符合规则。
- **固定顺序**：由生成器输出统一顺序，而非依赖人工排版。
- **文档镜像代码**：lint 检查 `doc_path` 与 `code_path` 的映射是否成立。

### 10.4 可选的代码对照能力

在需要进一步提高一致性时，可引入代码级对照能力，例如：

- 基于 `Clang AST` 抽取类型定义，与文档真源比对；
- 基于 `Tree-sitter` 做轻量结构解析；
- 在 CI 中检查生成结果、头文件变化与对象真源变化是否同步。

此类能力不是 SOSP 的前提条件，但对于大型仓库非常有价值。

---

## 11. Markdown 与 Typst 的职责分工

### 11.1 Markdown 的职责

Markdown 负责开发协作与日常维护，重点在于轻量、易读、易 diff、易纳入仓库管理。它适合承担以下职责：

- 日常浏览对象说明；
- 与代码一同维护；
- 在评审中直接查看 diff；
- 撰写草稿、模块说明和约定文档；
- 让开发者快速修改和补充内容。

### 11.2 Typst 的职责

Typst 负责正式文档输出层，重点在于排版质量和交付稳定性。它适合承担以下职责：

- 生成正式规格书、设计说明书和 PDF；
- 统一标题层级、编号、目录、页眉页脚；
- 提供交叉引用、图表编号、附录和索引；
- 控制版式一致性，使输出结果更专业、更稳定；
- 面向评审归档、外部提交和打印场景。

### 11.3 二者关系

二者的关系不是竞争，而是前后衔接：

```text
结构化源数据
    ↓
生成 Markdown（开发查看 / 协作维护）
    ↓
生成 Typst（正式排版 / 输出 PDF）
```

概括而言：**Markdown 偏开发协作，Typst 偏正式交付；二者都应建立在结构化真源之上。**

---

## 12. 推荐落地方案

结合前述原则，SOSP 的推荐落地方案如下：

### 12.1 真源选择

- 优先选择 `CUE` 作为源事实层；
- 若团队已有成熟工具链，也可使用 `YAML` 或 `JSON`；
- 无论选择何种格式，都应保证 schema 可检查、字段可约束、生成链路可稳定运行。

### 12.2 规则治理

- 通过 schema 约束对象必填项；
- 通过自定义 lint 检查唯一归属、层级边界、字段完整性和目录映射；
- 通过生成器统一顺序、标题层次和渲染样式；
- 通过 CI 检查生成结果是否为最新，以避免“真源已变、文档未更新”。

### 12.3 文档输出

- 面向开发日常阅读，生成 Markdown；
- 面向正式规格交付，生成 Typst，再输出 PDF；
- 若需要长期归档，可将 Markdown、Typst 和生成产物纳入版本管理或发布流程。

### 12.4 推进策略

工程落地时，建议采用渐进方式：

1. 先统一对象模板和模块文件结构；
2. 再建立项目级目录约定和 `common` 判定规则；
3. 随后引入结构化真源与生成器；
4. 最后在 CI 中补上 lint、生成校验与代码对照。

这样可以在不打断现有开发流程的前提下，逐步把对象说明体系升级为可治理、可检查、可交付的工程能力。

---

## 13. 结语

SOSP 的核心并不在于“把对象文档写得更漂亮”，而在于把对象说明从零散文本提升为一种**可治理的工程资产**。它要求对象有唯一归属、结构与语义分离、边界与可见性明确、文档层级映射代码层级，并通过结构化真源与自动化链路确保这些规则长期成立。

在这一框架下，Markdown 不再只是随手记录的说明文本，而成为结构化规格的可读界面；Typst 不再只是排版工具，而成为正式交付的输出终端。最终，SOSP 追求的是一种稳定的工程状态：对象定义明确、边界清晰、文档可信、变更可追踪、规则可检查、交付可生成。

这正是一个长期维护型系统所需要的对象文档范式。
